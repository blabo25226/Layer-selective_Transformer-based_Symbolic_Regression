## 0. ユーザーが行うこと

実装完了後、Colab実行開始時にユーザーが行う操作をここへまとめる。
Googleアカウントのパスワード、MFAコード、Drive承認はAIへ共有せず、必ずユーザー自身が入力する。

### 0.1 初回だけ行うこと

1. Codexへ「アプリ内ブラウザでGoogle Colabを開いて」と依頼する。
2. AIが開いたCodexアプリ内ブラウザのColab画面で、ユーザー自身がGoogleへログインする。
3. 作成済みNotebookをGoogle Driveの次のフォルダへ置く。

   ```text
   MyDrive/LTSR_colab/notebooks/
   ```

4. AIが作成したColab対応コードを次のいずれかでColabから取得可能にする。
   - 推奨: AIが許可済みのcommit・pushを行い、Colabから対象branch/commitをcloneする。
   - 代替: version付きsource archiveとSHA256を`MyDrive/LTSR_colab/source/`へ置く。
5. Colab Proのcompute units残量をColab画面で確認する。
6. `ランタイム` → `ランタイムのタイプを変更`でGPUを選ぶ。premium GPUやhigh-memoryを
   選択できる場合も、割り当ては保証されないため、実際のGPU名・VRAM・RAMを接続後に記録する。

### 0.2 セッション開始のたびに行うこと

1. Codexアプリ内ブラウザで対象Notebookを開く。
2. 右上の`接続`からランタイムへ接続する。
3. runtime typeがGPUであることを確認する。
4. Notebook先頭のDrive mountセルをユーザー自身が実行し、Google Driveへのアクセスを承認する。
5. mount後、次が見えることを確認する。

   ```text
   /content/drive/MyDrive/LTSR_colab/
   ```

6. Notebookの「ユーザー確認セル」に表示される次の値を確認する。
   - 対象branchとcommit
   - run IDと実行区分（smoke / pilot / paper）
   - GPU名、VRAM、RAM、local disk
   - Drive root
   - 前Phaseのresume元
7. 問題なければチャットで「Colab接続・Drive mount完了」と伝える。
8. 以降の通常セル実行、出力確認、エラー修正、再実行はAIへ委任する。

### 0.3 長時間run中にユーザーへ依頼する可能性があること

- Googleの再認証、MFA、Drive権限ダイアログ
- compute units残量の画面確認
- Colab側からの「接続を維持する」確認
- runtimeが終了した場合の再接続
- 実験条件変更、長時間runの中止、Pro+または別計算資源へ切り替える判断

認証が完了したColabタブは閉じず、同じCodexアプリ内ブラウザ内に残す。
AIが操作を再開できなくなった場合は、ユーザーが同じNotebookを開き直してから「再接続済み」と伝える。

## 1. 目的

`GPU_RUN.md`に定められたGPU実験を、Google Colab上でPhaseごとに確認・中断・再開できる形へ移植する。
各Phaseに対応するNotebookを作成し、ユーザーがGoogleアカウント認証、Google Driveのマウント、
Colabランタイムの選択と接続を行った後、AIがセルの実行、出力確認、エラー調査、修正、再実行を担当する。

ただし、研究ロジックをNotebookへ複製しない。Notebookは既存の`src/`と`scripts/`を呼び出す
薄い実行・監視層とし、評価設計、split、seed、集約、式保存の正本は既存Pythonコードに置く。

### 2.1 Colab Proについて確認した現行仕様

2026-07-26時点のGoogle公式情報では、Colab Proには月100 compute units、premium GPU、
high-memory machine、接続VMのterminalが含まれる。一方、GPU種類、最大VM寿命、idle timeout、
利用上限は動的で、Proでも資源は保証されない。compute unitsを使い切るとfree tier相当の方針へ戻り、
backendが終了する可能性がある。

一般のmanaged runtimeは可用性と利用状況に応じて最大約12時間である。
ブラウザを閉じても最大24時間継続できるbackground executionはColab Pro+の機能であり、
Colab Proの機能としては計画しない。

したがって、本研究では次を前提にする。

- Proによりfree tierより良いGPU・RAM・利用可能時間を期待できるが、特定GPUや完走を前提にしない。
- 接続後の実測GPU、VRAM、RAM、compute unit消費表示を基準に並列度と実行順を判断する。
- 1 Phaseまたは1 shardを12時間未満へ収め、seed/network単位の永続化とresumeを必須にする。
- Pro+のbackground executionがないため、長時間セル実行中はアプリ内ブラウザとNotebookを維持する。
- 12時間へ近づく見積りになったPhaseは、科学条件を変えずseed/network単位へ分割する。
- Colab内で`tmux`を使ってもmanaged runtimeの終了には耐えられないため、WSL手順の`tmux`をそのまま移植しない。
  実行中セルを前景で動かし、永続化とresumeで切断へ備える。

公式参照:

- [Google Colab FAQ: resource limits, runtime duration, Drive mount](https://research.google.com/colaboratory/faq.html)
- [Google Workspace: Colab Pro / Pro+の機能比較](https://knowledge.workspace.google.com/admin/getting-started/editions/google-workspace-add-ons)
- [Google for Developers: Colab Proは100 compute units、Pro+は500](https://developers.google.com/workspace/admin/reseller/v1/how-tos/products)
- [Colab runtime version FAQ](https://research.google.com/colaboratory/runtime-version-faq.html)

### 4.3 pipelineのPhase別実行

Phase 4–8を別Notebookから同一runへ安全に実行するため、既存pipelineへ最小限のPhase境界機能を追加する。
想定するインターフェースは`START_PHASE`、`STOP_AFTER_PHASE`、`RESUME=1`である。

- Phase 4 Notebook: 新規runを初期化し、Phase 4完了後に停止
- Phase 5 Notebook: 同じrunへresumeし、Phase 4をskipしてPhase 5完了後に停止
- Phase 6–8 Notebook: 同様に前段成果物を検査してから再開
- `START_PHASE`だけを指定して前提成果物がない場合はfail fast
- 従来どおり変数未指定ならPhase 4–8を一括実行し、既存GPU手順との互換性を保つ

この変更にはshell構文検査と、Phase境界・resume・manifest状態を確認するテストを追加する。
既存pipelineへ安全に追加できない場合は、pipelineを複製せず、Phase制御だけを行う小さなwrapperを作る。

## 5. Colab上の保存設計

### 5.1 コードと永続データ

- Google Driveには1TB以上の空きがあるため、保存容量は制約として扱わない。
- ただし、Drive容量が大きくてもColab VMのlocal disk容量は別であり、接続ごとに実測する。
- NotebookをDriveで開いただけでは、Windows上の
  `C:\Document\researches\LTSR`やNotebookの隣にある`src/`、`scripts/`はColab runtimeから見えない。
- Notebookの保存場所、実行時のcurrent working directory、Python import pathは別物として明示的に設定する。
- Colabが参照する完全なsource treeを、remote branch/commitまたはDrive上のversion付きarchiveから
  `/content/LTSR`へ復元する。
- 復元後に`cd /content/LTSR`し、`PYTHONPATH=/content/LTSR/src`を設定する。
- branch、commitまたはsource archive SHA256がNotebook内の期待値と一致しなければ停止する。
- checkpoint、DREAM4、GSE112372、raw run、archive、source archiveはGoogle Driveへ永続保存する。
- Drive上で大量の小ファイルを直接読み書きすると遅いため、実行中のsourceと高頻度I/Oは原則`/content`を使う。
- Drive公式FAQでも、多数の小ファイルを直接読むよりarchiveをlocal VMへコピーして展開する方法が推奨されている。
- 各Phase終了時だけでなく、Phase 4はseed完了時、Phase 5–8はseed/network shard完了時、
  異常検知時にもrun directory、ログ、manifestをDriveへ増分同期する。
- 同期は一時名へコピーしてからrenameするか、SHA256/JSON parse確認後に完了sentinelを置き、
  途中コピーを完成成果物と誤認しない。
- checkpointはDriveにcacheし、Colab VMへコピーまたは安全なリンクを作る。毎回再downloadしない。
- Colab VM切断後に`/content`だけへ残った結果は失われるため、Phase/shard完了をDrive同期完了前に宣言しない。
- Driveの各runは専用subfolderへ分け、単一folder直下へ1万件規模のファイルを置かない。

Drive上の想定rootはユーザーがセルで明示する。例:

```text
/content/drive/MyDrive/LTSR_colab/
  notebooks/
  source/
  checkpoints/
  data/
    dream4/
    human/
  runs/
    <run-id>/
  archives/
  logs/
```

### 5.2 Notebook以外のファイルをColabへ渡す方法

Notebookは単独では実行できない。`src/`、`scripts/`、`configs/`、`NSRS/`、`TPSR/`、
`requirements/`、テスト、設定JSONが必要である。実行時は次のどちらかで完全なsource treeを作る。

#### 方法A: Git clone（推奨）

次のbashはWindowsやCursorのterminalではなく、Google Colabの**コードセル**で実行する。
Colabではセル先頭に`%%bash`を置くとセル全体をbashとして実行でき、1行だけなら`!git ...`の形式も使える。
directory移動を後続セルへ維持する場合は`!cd ...`ではなく`%cd /content/LTSR`を使う。
実装するNotebookでは手入力を避けるため、この操作を準備済みセルとして提供する。

```python
# Colab code cell
%cd /content
```

```bash
%%bash
set -euo pipefail
git clone --branch 20260726/gpu-scale-prep-colab --single-branch \
  https://github.com/blabo25226/Layer-selective_Transformer-based_Symbolic_Regression.git \
  /content/LTSR
cd /content/LTSR
git checkout <承認済み固定commit>
```

利点はcommit provenanceが明確なこと、欠落ファイルが起きにくいこと、sourceをDriveへ大量コピーしなくてよいことである。
今回、実装完了後の`git add`、`git commit`、`git push`、`git pull`はユーザーが許可済みである。
Colab Proには接続VMのterminal機能もあるが、本計画ではterminalを必須にせず、再現可能なNotebookセルから実行する。

#### 方法B: Driveのsource archive

```text
MyDrive/LTSR_colab/source/
  ltsr_<commit-or-version>.tar.gz
  ltsr_<commit-or-version>.tar.gz.sha256
```

NotebookがSHA256を確認して`/content/LTSR`へ展開する。
`.git/`、checkpoint、raw result、外部データをarchiveへ混ぜない。
archive内容のversionと実行manifestを対応づける。

どちらの方法でも、Drive mount pathをrepo rootだと仮定して相対importしない。
Notebookの先頭で`REPO_ROOT=/content/LTSR`を設定し、すべてのコマンドをそのrootから実行する。

### 5.3 run識別

run IDは既存runと重複させず、用途を名前で分ける。

```text
colab_smoke_YYYYMMDD_01
colab_pilot_YYYYMMDD_01
colab_paper_YYYYMMDD_01
```

同じrun IDへ異なる設定の結果を混ぜない。機構的な中断からの再開だけ`RESUME=1`を使う。
実験設定または計算コードを変更した場合は、新しいrun IDと新しいmanifestを使う。

## 6. PhaseごとのColab実行可能性

結論として、Phase 0–8はすべてColabで実行可能な見込みがある。ただし、現状のスクリプトを
そのまま1セルで最後まで流すだけでは、Phase 0のPython互換性、Phase 4/7のruntime上限、
Phase 6のCPU-bound探索、Drive同期により本実験の完走を保証できない。

| Phase | Colab可否 | 主な資源・時間 | 主な問題 | 計画する対応 |
|---|---|---|---|---|
| 0 | 条件付きで可能 | setup中心 | 現行Colab runtimeはPython 3.12系で、Hydra 1.0との互換性が懸念 | 利用可能ならpast runtimeのPython 3.11を優先し、なければPython 3.10環境を構築。preflight不合格なら後続を開始しない |
| 1 | 可能 | 主にCPU、短時間 | Notebook単体ではgeneratorと`src/`が見えない | 完全source treeを`/content/LTSR`へ復元し、出力を診断用runへ分離 |
| 2 | 可能 | GPU推論＋CPU/Julia PySR | PySR初回install、BFGS、Julia compileに時間 | install cache、smoke、方法別時間記録。最終設定選択には使わない |
| 3 | 可能 | GPU fine-tuning | legacy pilotと本実験rankingの混同 | 実装確認専用とし、Phase 4のlive validation rankingへ影響させない |
| 4 | 条件付きで可能 | GPU学習＋decode。既存GPU PCで5 seed約6.3時間 | Colab Proの一般的な最大runtimeへ近づく可能性。現状はPhase全体のsentinelでresume | seed単位checkpoint/resume、各seed直後のDrive同期、aggregate再構築を実装 |
| 5 | 可能 | GPU学習＋CPU BFGS/SymPy | 条件数とrandom層集合が多い。CPU競合 | 既存seed並列を実測VRAM/RAMから段階的に上げ、seed単位resumeを利用 |
| 6 | 条件付きで可能 | TPSR/MCTS、BFGS、SymPyがCPU-heavy | 4条件×問題数でも時間爆発しやすい | `noise=0.1`だけを実行し、240秒TPSR decode timeout、10秒SymPy timeout、seed resumeを使う |
| 7 | 条件付きで可能 | Size10/100、各5 networks、全target | `EVAL_LIMIT`が効かず、1 seedでも長時間化し得る | seed×size×network shard、network完了ごとのDrive同期、最終aggregate |
| 8 | 可能 | 4 donor LODO×複数seed、PySR | PySRとBFGSがCPU-bound、donor数は増えない | seed単位resume、fold進捗記録、式とfailureを逐次保存 |
| 最終検査 | 可能 | CPU/Drive I/O | 多数の小ファイルと途中同期 | localで検査後、tar.gz＋SHA256をDriveへ保存し、Drive側で再確認 |

### 6.1 Python runtimeのgo/no-go

Google公式のruntime version FAQでは、2026-07-26時点でPython 3.11を含む過去runtimeが掲載されている一方、
過去runtimeはリリース後1年間だけ提供され、選択肢は変化する。Notebookへ特定runtimeの存在を決め打ちしない。

優先順位は次のとおりとする。

1. Colabのruntime typeで利用可能なPython 3.11過去runtimeを選び、GPUと全preflightを確認
2. 利用できなければ、現行runtime内にPython 3.10互換環境を構築し、runtime再起動後に再確認
3. PyTorch CUDA build、Hydra、NeSymReS、TPSR、PySRのsmokeがすべて通らなければ実験を止める

Python 3.12で偶然importできたことだけを合格にせず、checkpoint loadと最小train/decodeまで確認する。

### 6.2 Phase 4の追加resume要件

現行`phase4_multiseed.py`は各seed終了時にseed別JSONを書いているため、部分成果物自体は残る。
一方、pipelineは最終`layer_ranking_scores.json`だけをresume sentinelにしており、中断時に完了seedを再利用できない。

Colab対応では次を追加する。

- Driveから復元した`contrib_seed*`、`raw_scores_seed*`、`absolute_improvements_seed*`、
  `contribution_status_seed*`、`tuning_seed*`、`equations_seed*`をschema検査
- 完全なseedだけskipし、不完全なseedは同じseedで最初から再実行
- 全seedが揃った後、保存済みseed別rawデータからaggregate/ranking/stabilityを再構築
- 完了seedを別commit・別設定から流用しない。manifestのcommit・設定一致を必須にする

### 6.3 Phase 7の追加shard要件

Phase 7は`--all-nets`を1 processで流す現行形より、同じ設定のままnetwork単位へ分割する方が
Colabのruntime上限に適する。乱数、train/test split、target範囲を変えず、実行単位だけを分ける。

- shard keyを`seed / size / network`とする
- Size10/100ともnetwork 1–5を個別実行できるようにする
- 各network完了時に問題単位式、regulator selection、時間、failureをDriveへ同期
- aggregateは全必須shardが揃うまで作成しない
- smokeのtarget制限結果と本番の全target結果を別runへ保存する

## 7. 実装順序

### Step 1: 現行Colab Notebookとpipelineの監査

- `notebooks/run_on_colab.ipynb`から再利用できるセットアップ処理だけを抽出する。
- Colabの現行Python、CUDA、PyTorch互換性を実行時に表示し、記録する。
- Python 3.12へ無理に合わせず、Hydra 1.0とNeSymReSが動くPython環境を確認する。
- `requirements/gpu.txt`と`requirements/colab.txt`の役割を整理する。
- Colabで不要なTPSR E2E checkpointをdownloadしない。Phase 6はNeSymReS backboneを使用する。

### Step 2: Phase別実行とresume機能

- Phase 4–8の境界実行を実装する。
- Phase完了成果物が揃うまで次Phaseへ進めない。
- 途中失敗時にmanifestの`status`と該当stageを失敗として残す。
- resume時は最終成果物の存在だけでなく、必要に応じてJSONの読み込み可否も確認する。
- Phase別実行でもbranch、commit、dirty状態、checkpoint SHA256、環境、主要設定をmanifestへ残す。

### Step 3: Notebook作成

各Notebookの構成を統一する。

1. 目的、入力、出力、前提Phase、概算コストをMarkdownで表示
2. ユーザー操作が必要な認証・Drive・runtime接続セル
3. Git cloneまたはDrive archive展開を行う最小bootstrapセル
4. `REPO_ROOT=/content/LTSR`へ移動し、repo commit/source SHA256と作業ツリーを確認
5. repo内の共通Colab helperをimport

## 8. エラーと計算時間爆発への対応

### 8.1 自動的に調査・修正してよい範囲

- import、path、Colab固有shell、依存関係、Drive同期の不具合
- 明らかなコードバグで、split、seed、探索予算、評価条件を変えない修正
- smoke失敗
- JSON/report/archive生成や表示だけの失敗
- GPU/CPU/RAM/disk使用量の計測追加
- 問題単位timeoutが正しくfailureとして記録されるための機構的修正

修正後は関連テストを実行し、計算コードを変更した場合は本番run IDを新しくする。

### 8.2 ユーザー確認が必要な範囲

- seed、epoch、LR grid、noise、beam、BFGS、TPSR rollout/horizon/widthの変更
- `EVAL_LIMIT`、DREAM4 target/network範囲、random layer集合の縮小
- timeout値を短くして評価不能を増やす変更
- 採用条件やvalidation schemaを緩める変更
- OOM回避のためのbatch、並列度、モデル、精度形式の変更が実験条件へ影響する場合
- 想定時間を大きく超えたrunの中止・縮小
- 同一原因で3回失敗した後の続行
- 完了run、Drive上のraw結果、archiveの削除

### 8.3 計算時間爆発の検知

各Phaseで次を記録する。

- 開始時刻、問題またはseed単位の経過時間、予測残時間
- `nvidia-smi`相当のGPU使用率とVRAM
- CPU、RAM、Drive/local disk残量
- 現在のseed、condition、noise、network、target
- 最終ログ更新時刻

次のいずれかを異常候補とする。

- smoke実測から外挿した予測時間を大幅に超える
- 同一問題でログ更新がなく、既定timeoutも働かない
- VRAM/RAMが継続的に上限へ張り付く
- Drive同期が計算時間の支配項になる
- SymPy、BFGS、PySR、TPSRの1問題が異常に長時間化する

異常時はまずスタック、ログ、進行中の問題を保存する。設定を勝手に縮小せず、
既存の問題単位timeout、resume、失敗理由保存を優先して修復する。

### 8.4 `GPU_RUN.md`付録Bの計算緩和策

付録Bと現行HEADで実証済みの工夫を、結果を変えないものから優先してColabへ反映する。

#### 設定を変えず適用する

- **Phase resume**: `RESUME=1`で完了済みPhase/seed/networkをskipし、前段を再計算しない。
- **Phase 4/input_dataの温存**: 完了済みPhase 4とrun-local inputをDriveへ保存し、
  Phase 5以降の再開時に同じcommit・設定・checksumを確認して復元する。
- **seed並列**: Phase 5–8は既存`MAX_PARALLEL_SEEDS`を使用する。
  まず1 processのVRAM/RAM/CPUを測り、1 → 2 → 3 → 最大5の順に安全な上限を決める。
  4070 Ti SUPERでの「1 process約1.5GB」はColab割当GPUへそのまま仮定しない。
- **SymPy timeout**: `symbolic_recovery`と`skeleton`の重い処理に既存10秒timeoutを維持する。
  timeoutは「等価と証明できず」と保守的に記録し、成功例だけの指標へ混ぜない。
- **TPSR timeout**: 現行HEADの`LTSR_DECODE_TIMEOUT_SEC=240`をNotebook設定とmanifestへ明示する。
  timeoutした問題はfailureとして残し、valid率とfailure-penalized指標へ反映する。
- **shard直後の同期**: 完了seed/networkをDriveへ即時同期し、runtime終了時の再計算を減らす。
- **archive利用**: 多数の小ファイルをDriveから直接読むのではなく、source/dataをarchiveでlocal VMへ移す。

#### 実測後に適用する

- CPU競合が強い場合だけ`OMP_NUM_THREADS`、`MKL_NUM_THREADS`等を制限する。
  BLAS reduction orderが変わり得るため、値をmanifestへ記録し、変更前後を同じrunへ混ぜない。
- high-memory machineやpremium GPUは利用可能なら使うが、特定機種を前提に設定を変更しない。
- GPU使用率が低くCPUが支配しているPhase 6/7では、より高価なGPUへ切り替える前に
  CPU時間、BFGS、SymPy、TPSRの内訳を確認する。

#### ユーザー承認済みのPhase 6縮小

- Phase 6は全実行区分で`NOISE="0.1"`だけを使用する。
- `0.0 / 0.05 / 0.2`は計算量緩和のため省略する。
- 計算量は4水準実行のおおむね4分の1になる見込みだが、H3のノイズ頑健性slopeは算出できない。
- Phase 6は`noise=0.1`でのFT主効果、TPSR主効果、交互作用だけを評価する。
- manifest、Phase 6 report、公開summary、provenance noteへ単一noiseであることを記録する。
- `GPU_RUN.md`のColab手順と本計画の設定を一致させ、4水準を実行したように記述しない。
- 既存の4水準CPU pilotや別GPU runと同じ実験条件として集約しない。
- per-problem並列は乱数スキームと結果を変え得るため採用しない。
- seed数、random layer集合、network、target、beam、BFGS、TPSR budgetは自動削減しない。

## 10. Git運用

- 実装前後に`git status --short`とbranchを確認する。
- Notebook生成時に既存のユーザー差分を上書きしない。
- コード、テスト、Notebook、文書を意味のまとまりごとに分ける。
- commit前に`git diff --check`、compileall、pytest、shell syntax、Notebook検査を行う。
- 今回は`git add`、`git commit`、`git push`、`git pull`が明示的に許可されている。
- ユーザーも同じbranchでGit操作を行う可能性があるため、作業開始時だけでなく、
  `add`、`commit`、`pull`、`push`の各操作直前にbranch、`git status --short`、HEADを再確認する。
- `git add`は今回変更した明示的なpathだけを指定し、ユーザーの別変更や未追跡ファイルを一括stageしない。
- commit直前にstaged diffを再読し、想定外の差分が入った場合はcommitせず切り分ける。
- remote更新の取り込みは`git pull --ff-only`を使う。fast-forwardできない場合は勝手にmerge/rebaseせず、
  現在のlocal/remote HEADと競合内容をユーザーへ報告する。
- pushがnon-fast-forwardで拒否された場合は、再度statusとremote更新を確認し、同じ安全手順を繰り返す。
- force push、履歴改変、ユーザーcommitの上書きは行わない。
- Colabでは固定commitをcheckoutし、本番run開始後に`git pull`しない。
